# ADR 0011: Deterministic development agents

Status: Accepted (PR 11)

## Purpose and scope

A fake CLI completes the real multi-agent execution loop without an AI provider,
network request or LLM. It is reusable for local demos and backend/browser tests.
It does not interpret tasks, orchestrate agents or execute shell commands. The
`task` message type is mapped to a fixed text response, not a task execution system.

## Runtime integration and execution boundary

Creating an agent accepts only an optional `providerId: "fake"` (or null). The
selection is persisted in the existing agent record. Unknown executable, argument,
environment, cwd and status fields remain stripped. Other provider IDs are rejected.
Default/null agents continue to launch the existing allowlisted local shell.

AgentRuntimeManager uses one small server-owned `resolveRuntimeCommand` function.
For fake it returns `process.execPath`, a fixed CLI entrypoint, and fixed environment
keys. PtyManager accepts this internal command selection while retaining the same
cwd validation, session tracking, output attachments and process-tree termination.
The WebSocket gateway constructs its own PTY options and never forwards commands,
arguments or environment from browser payloads. There is no generic provider registry.

The app enables fake agents only in development/test (`!config.isProduction`).
Production rejects creation and launch of persisted fake agents; unsupported persisted
providers fail safely rather than quietly starting a shell. No fake option or real AI
availability is added to the UI. Development provisioning uses the fixed REST selection.

Source launches use the installed tsx loader with an absolute fixed CLI source path.
Build emits a sibling `dist/fake-agent.js` Node bundle, which the bundled server selects
without a TypeScript loader. No shell interpolation is used. Both macOS and Linux use
the actual node-pty implementation. Windows retains existing best-effort PTY behavior;
the Node CLI itself uses portable APIs, but PR 10's hard-link/directory-fsync requirements
still apply.

## Identity, workspace and mailbox semantics

The runtime supplies `QELVRA_AGENT_ID` and `QELVRA_DATA_DIR` from server-owned identity
and configuration. The CLI validates the ID, requires its own fake record, and verifies
its actual cwd equals the validated workspace. Inbox/outbox locations are resolved by
AgentWorkspaceManager, not user-provided paths. It opens fresh read-only registry
snapshots for operations, allowing newly created recipients to become visible without
writing registry state. Sender always derives from the configured ID.

The CLI reuses MailboxManager and the exact PR 9 message schema. It only lists/reads its
own inbox, publishes into its own outbox and acknowledges its own incoming messages.
It imports no router, PTY or runtime service and never writes another inbox. MessageRouter
performs all delivery. Incoming fields remain unchanged; result IDs/timestamps are
generated by production MailboxManager.

Outbox publication now also syncs the destination directory using the existing exclusive
atomic helper. A processor publishes a complete response before acknowledging the
matching incoming snapshot. Failed publication leaves the incoming envelope. A small
in-memory map retains response identity when acknowledgement fails; subsequent attempts
reuse that response until acknowledgement succeeds. Failed operations produce controlled
codes in the terminal, never raw errors or paths in server logs.

## Commands and deterministic behavior

| Command                        | Behavior                                                                 |
| ------------------------------ | ------------------------------------------------------------------------ |
| `PING`                         | Prints `PONG`                                                            |
| `ECHO hello`                   | Prints `hello`                                                           |
| `STATUS`                       | Prints `READY <agent-id>`                                                |
| `SEND <recipient> <body>`      | Publishes a `message`, prints `MESSAGE_QUEUED <id>`                      |
| `SEND_TASK <recipient> <body>` | Publishes a `task`, with the same queue confirmation                     |
| `CHECK_INBOX`                  | Prints count and validated envelope/body summaries                       |
| `RESPOND`                      | Processes eligible messages once and acknowledges them after publication |
| `AUTO_RESPOND ON/OFF`          | Enables/disables periodic processing                                     |

`message` produces `result` with `ACK:<body>`; `task` produces `result` with
`DONE:<body>`. Bodies are opaque text, never executable instructions. `result`, `status`
and `error` never trigger replies and remain available for `CHECK_INBOX`. This prevents
result ping-pong even when both agents have auto response enabled. User-facing bodies
are JSON escaped in inbox summaries so control sequences are printed as data.

AUTO_RESPOND is on at startup. An immediate scan handles backlog, then a 500 ms timer
queues scans. Commands/scans are serialized; missed ticks are skipped while scanning,
preventing overlap or busy loops. Polling stops on EOF, terminal Ctrl-C, SIGHUP, SIGINT
and SIGTERM. Shutdown gates queued work, lets an underway publication/acknowledgement
finish, and exits; runtime process-tree cleanup remains the final owner.

## Persistence and limits

A stopped agent receives inbox data normally and processes it after startup. Restart
starts AUTO_RESPOND ON again; mode changes are process-local. SIGKILL is recorded as an
unexpected runtime exit/error. Mailbox files survive, and restart scans pending inboxes.
No long-term memory or persistent consumed-ID ledger is added.

Processing is at-least-once. A crash between response publication and incoming
acknowledgement can generate a second response after restart; the map only prevents
duplicates within the same live process. Router idempotency concerns an envelope ID,
not exactly-once application processing. Source/inbox races inherit PR 8/9/10's same-user
trust model. Fake agents are not an OS sandbox. Registry snapshots can become stale
between reads; the router rechecks recipient registration at delivery.

Adding ACK/DONE may exceed the unchanged 64 KiB body limit; that response fails and the
incoming message stays pending. Invalid inbox entries are reported/preserved, not
silently deleted or quarantined by this CLI. Results remain on disk until explicitly
acknowledged by another future consumer. Each poll reads a registry snapshot and lists
the inbox, suitable for a bounded development demo rather than large-scale deployment.

## Verification and future providers

Real runtime/PTY tests cover round-trip, three agents, stopped delivery, restart, crash,
five-agent concurrent delivery, failed publication and production gating. Real server
SIGINT/SIGTERM tests assert every fake PID exits and pending messages survive. Browser
E2E sends a command through xterm and reads the returning inbox result. All fixtures
use disposable DATA_DIR and owned-process cleanup. A manual smoke script exercises
the same runtime/PTY path without bypassing delivery.

See [verification and demo](../verification/pr11-fake-agent.md) for commands/results.
Real providers can later supply a server-owned command descriptor through this seam.
Provider management, real API integrations, intelligence, tasks and PR 12 are deferred.
